# 注文端末との統合照合表

Issue #240 作業3「注文端末チームとの統合準備」の成果物。仕様待ちでも作成できる照合表・組み込み条件・仕様受領後の確定事項をまとめる。コードは変更しない。

## 0. 読み方と前提

- 根拠は `ファイル:行` または節で示す。行番号は `main`（dd0c988）時点。`order-client.js` は PR #270（Issue #263）未マージのため、#270 で変わる箇所は「#270 適用後」と明記する。
- 「推測」と書いた記述は、コードやドキュメントから直接確認できていない。
- 区分の意味は次のとおり。
  - 確定: 現行コードが実際にそう動く。または注文端末チームの仕様として文書に確定と書かれている。
  - 仕様待ち: 注文端末チームの仕様受領後に決める。現時点の値を確定APIとして扱わない。
- 比較対象は三者。
  - 現行API: `POST /api/orders`（中継サーバー、既定8000番）。`relay-server/order-intake.js`、`relay-server/routes/orders.js`。
  - order-client: 端末側モジュール `order-client.js`。
  - 独立DBモック: `relay-server/database.js`・`relay-server/schema.sql`（[order-database.md](order-database.md)）。HTTP APIを持たない。
- 参考として、[注文サーバー接続](注文端末_注文サーバー接続.md)（2026-09-11確定と記載）にある注文画面→既存注文サーバー（既定3001番、`menuId` 方式）も併記する。ただしサブモジュール `order-terminal` はこのワークツリーで未取得で、正本の `ORDER_API.md` は確認できていない。3001番側の型・上限は本書では確定扱いにしない。

### 2.2 組み込み時に端末側が満たすべき条件

同一origin

1. 注文画面と `/api/orders` を同じスキーム・ホスト・ポートで配信する。3001番（注文サーバー）上の画面とrelayの8000番は別originになるため、そのままではclientを使えない（推測。画面の配信元がどこになるかは未確認）。リバースプロキシの同一origin化か、relayでの画面配信かを決める。
2. 配信元のスキーム・ホスト・ポートを後から変えると、端末の未送信キュー（IndexedDB）が別DBになり取り残される。運用開始前にoriginを固定する。
3. 画面・`order-client.js` を relay から配信する場合は、`routes/static.js` の許可リストへ追加が必要（画面統合時の作業。本書の対象外）。
4. 1端末1タブ1クライアント。複数タブの排他制御は未実装（[組み込み](注文端末_通信モジュール組み込み.md)）。

認証

5. トークンを設定する運用では、端末が事前にQR等でCookieを取得しているか、`getToken` でBearerを渡す。トークンはキューに保存しない。
6. 401は `failed` で停止する。設定を直した後は画面から `orders.retry(orderId)` を呼ぶ導線が必要。
7. 公開する範囲を決める。ゲストWi-Fiから8000番へ到達できない構成を前提とする（[通信仕様](注文端末_中継サーバー通信仕様.md) §10）。

HTTPS

8. 画面がHTTPSなら、送信先もHTTPSにする。HTTPSの画面からHTTPの送信先は一般にブラウザが遮断する（推測。一般的なブラウザ仕様）。
9. 端末が信頼する証明書の配布方法を決める。この手順は未整備。
10. プロキシで終端する場合は `RELAY_COOKIE_SECURE=1` と `RELAY_TRUST_LOOPBACK=0` を設定する。

送信状態表示

11. `submit` の戻りは端末への保存完了であり、受付完了ではない。受付完了は `sent` だけで表示する。
12. 「送信中」「送信済み」「送信できていない」「要確認（`needs_review`）」を利用者が区別できる表示にする（[通信仕様](注文端末_中継サーバー通信仕様.md) §9）。
13. `submit` 成功後は同じカートの再確定を防ぎ、失敗時はカートを保持する。二重タップ防止は画面側の責務。
14. `failed` は `HTTP 4xx` としか記録されない（D23）。理由表示が必要なら要件として決める。
