# 現行KDSブラウザ回帰試験・受け入れ記録（Issue #204）

対象Issue: [#204 KDS: 現行UI変更を対象にブラウザ回帰試験を実施し、受け入れ可能な基準版を確定する](https://github.com/itiwoja/pokapoka-system/issues/204)

## この記録の位置づけ

この記録は、2026-07-14時点の旧版スモーク確認を、現行作業ツリーのKDS UIへ無条件に適用しないためのものです。ローカルMOCKで再現できるブラウザ回帰と、店舗の実機・店内LAN・実プリンター・TableCheck LIVEが必要な導入前受け入れ試験を分けて記録します。

ローカル確認が合格でも、iPad・KDS実機2台・注文端末・店舗ネットワーク・実プリンター・TableCheck LIVEの合格を意味しません。実機項目は [実機検証チェックシート](実機検証チェックシート_受け入れ試験.md) へ記録し、必要な前提がない場合は `保留` とします。

### 安全な記録ルール

- APIキー、共有トークン、Cookie、Authorizationヘッダー、個人情報、実IP、SSIDは記録しない。
- TableCheck LIVEのレスポンスを保存せず、必要な場合は匿名化したテストID・件数・statusだけを記録する。
- ブラウザコンソールやネットワークログを残す場合は、認証情報・URLの機密部分・個人情報を除去する。
- `127.0.0.1` での結果を店内LAN接続やゲストWi-Fi隔離の証跡に使わない。

## ローカルブラウザ回帰シナリオ

### REG-01 起動・MOCK予約の反映

- 操作: `/` と `/demo` を開き、予約を1件作成する。人数変更とキャンセルも行う。
- 期待結果: KDSが表示され、予約が予約ストックへ反映され、変更は上書き、キャンセルは消去される。
- 実測結果: main作業ツリーのMOCK `/demo`で予約作成は成功し、`/api/stock`には反映されたが、修正前の`/`では約10秒後もKDS予約ストックへ反映されなかった。ルートHTMLに実際のbridge script要素がなく、relay-serverの注入判定が説明コメント中の文字列を誤認していた。plan16で判定をscript要素へ修正し、修正後の隔離MOCK環境では`/demo`作成→`/api/stock`→KDS予約ストック反映を約4.5秒で確認した。
- 合否: `保留（作成・反映のみ確認）`
- 証跡 / 不具合Issue: 修正内容は`relay-server/server.js`と`relay-server/server.test.js`。修正後の隔離MOCKで作成・反映は確認済み。人数変更・キャンセルの上書き／消去は固定フィクスチャで再確認すること。

### REG-02 予約ストックから進行中への移動

- 操作: 予約へ卓番を入力し、「着手/配膳へ」を実行する。
- 期待結果: 予約が進行中へ移動し、卓番・人数・メニューが保持される。上流の予約データを書き換えない。
- 実測結果: 予約ストックのカードで卓番をA1に設定し、着手操作を行った。予約ストックは4件から3件へ減少し、進行中にA1のカードが表示された。
- 合否: `保留（UI確認）`
- 証跡 / 不具合Issue: ブラウザ表示のDOM要約のみ。上流予約データを書き換えていないことは通信・状態計測を伴う再確認が必要。

### REG-03 品目の一部完了・全品完了・復元

- 操作: 複数数量の品目を1個ずつ完了し、全品目を完了する。表示消去と提供時間記録を確認する。必要なら既存の完了undoを実行する。
- 期待結果: `0/3 → 1/3 → 2/3 → 完了` の順で更新し、全品完了後にカードが自動消去される。undoは対象カードだけを戻す。
- 実測結果: A5の複数数量品目で表示が`0/2`→`1/2`→完了へ更新し、最後の品目完了後にA5カードが表示から消えた。
- 合否: `保留（完了・消去確認）`
- 証跡 / 不具合Issue: ブラウザ表示のDOM要約のみ。完了undoと提供時間記録は未確認。

### REG-04 ホールA/B/C比較表示

- 操作: ホールモードへ切り替え、A・B・Cを順に選択してリロードする。その後キッチンへ戻る。
- 期待結果: Aは進行中＋予約、Bは予約主表示＋進行中compact、Cは提供準備完了＋予約＋進行中summaryを表示する。選択はホールだけに表示され、キッチンのgrid/lane操作へ影響しない。
- 実測結果: ホールA・B・Cを順に表示し、各パネルの表示を確認した。Cを選択した状態でリロードしてもCが保持され、キッチンへ戻すとgrid表示へ復帰した。
- 合否: `合格（ローカルUI）`
- 証跡 / 不具合Issue: ブラウザ表示のDOM要約のみ。

### REG-05 炊飯準備cue

- 操作: rice品目を含む予約と含まない予約、予約時刻まで31分以上・30分以内・時刻超過の予約を用意する。キッチンとホールでcueを確認し、キッチンで確認操作を行う。
- 期待結果: rice予約の30分以内・時刻超過だけにcueが出る。確認状態は当日中保持され、ホールから変更できない。非riceまたは31分以上には出ない。
- 実測結果: rice品目のcue表示を確認し、キッチン側の確認操作で表示が`炊飯準備`から`炊飯準備（確認済み）`へ変化した。ホール側では確認ボタンを操作できないことを確認したが、31分以上・30分以内・時刻超過と非riceの全境界ケースは同一フィクスチャで網羅できなかった。
- 合否: `保留（部分確認）`
- 証跡 / 不具合Issue: 境界値を固定した匿名MOCKフィクスチャで再実施する。

### REG-06 厨房限定卓番上書き

- 操作: キッチンで進行中注文の卓番を変更し、同じ卓番を別の進行中注文へ入力する。重複警告をキャンセルした場合と、2回目の明示許可をした場合を確認する。ホールでも操作可能範囲を確認する。
- 期待結果: 表示・伝票プレビュー・提供準備完了表示・コンロ所有表示だけが実効卓番を使う。元のorder、`window.KDS_ORDERS`、上流APIは変更しない。重複は最初に保存されず、同じ候補の再確認後だけ保存される。ホールからは変更できない。
- 実測結果: A3の卓番上書きUIでB9を選択し、カード表示が`卓 B9`へ変化した。修正前のrootではbridge不在により`window.KDS_ORDERS`を取得できず、元order・上流APIを変更していないことの確認までは完了しなかった。
- 合否: `保留（UI確認）`
- 証跡 / 不具合Issue: bridge修正後に安定したMOCK orderを用い、元order・`window.KDS_ORDERS`・上流API非変更と重複時の2段階確認を再確認する。

### REG-07 提供準備完了cueと独立undo

- 操作: 全品目完了後にホール表示へ切り替え、提供準備完了cueを確認する。dismiss、専用undo、リロードを行い、厨房の完了undoとは別に動作することを確認する。
- 期待結果: 完了直後にeffective卓番・完了時刻・品目要約を持つcueが1件だけ作られる。dismiss済みの復元操作は6秒の専用undoで行い、厨房側の完了状態・undoとは干渉しない。
- 実測結果: A5の全品目完了後、ホールCに提供準備完了cueが表示された。dismissで表示から消え、専用undoでcueが復元された。厨房側の完了操作を戻すテストまでは行っていない。
- 合否: `保留（dismiss/undo確認）`
- 証跡 / 不具合Issue: ブラウザ表示のDOM要約のみ。リロード後の保持と厨房側完了undoとの非干渉は未確認。店舗運用・別端末同期は実機E2Eへ分離する。

### REG-08 同一origin 2タブ同期・リロード

- 操作: 同じURLを2タブで開き、品目完了、コンロ、タイマー、並び順、ホールcue、炊飯cue、卓番上書きの変更を片方で行う。両タブをリロードする。
- 期待結果: 同一originの2タブではLocalStorage/BroadcastChannelにより状態が収束し、リロード後も当日分が保持される。別端末同期はこのローカルシナリオの合格対象外として実機E2Eへ分離する。
- 実測結果: 2タブを開いて片方の品目完了を操作したが、修正前rootのbridge不在と動的MOCK order IDの差異があり、同一orderを対象とした有効な収束試験にならなかった。リロード後の保持を含め、合格判定は行わない。
- 合否: `保留`
- 証跡 / 不具合Issue: 固定orderを投入できるMOCKフィクスチャで、plan16修正後に再実施する。別端末同期の合格とは混同しない。

### REG-09 印刷プレビュー・ブラウザフォールバック

- 操作: 注文単位の印刷プレビューを開き、プリンターIP未設定の状態で印刷を実行する。
- 期待結果: 全品目を含むプレビューが開き、実機送信を行わずブラウザ印刷へフォールバックする。実機の紙面品質や先頭`@`はこのシナリオの合格対象外とする。
- 実測結果: 注文カードから`伝票プレビュー`を開き、全品目と印刷・閉じる操作を確認した。プリンター未設定時の実際のブラウザ印刷ダイアログ起動までは実行していない。
- 合否: `保留（プレビューのみ）`
- 証跡 / 不具合Issue: 実機送信・紙面品質・先頭`@`はE2E-07へ分離する。

### REG-10 コンソール・通信境界

- 操作: REG-01〜09を実行し、コンソールのerror/warning、外部ネットワーク通信、注文・予約の上流書込みを確認する。
- 期待結果: error/warningがなく、許可されたloopbackのMOCK/API以外へ通信しない。UI追加状態は同一originの保存・同期だけで完結し、上流POS/TableCheckへ書き戻さない。
- 実測結果: main作業ツリーとplan16修正後の隔離環境で、ブラウザ開発者ログのerror/warningは0件だった。隔離環境ではbridge scriptが1件だけ注入されることを確認した。外部通信と上流書込みの全操作については、ネットワークログを保存せずに網羅確認するところまでは完了していない。
- 合否: `保留`
- 証跡 / 不具合Issue: 記録には秘密情報を含めず、修正後の固定フィクスチャでネットワーク境界と上流非変更を再確認する。
