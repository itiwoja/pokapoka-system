# 中継サーバー―デシャップモニター WebSocket配信仕様

## 1. 目的

本書は、店内の中継サーバーからデシャップモニターへ注文状態をリアルタイム配信するためのWebSocket通信方式を定義する。

配信対象は画面映像ではなく、注文の初期スナップショットおよび追加・更新・取消の差分イベントである。デシャップモニターは受信した注文データをブラウザー上で描画する。

今回の検証では、中継サーバー内にモック注文を保持し、実際のタブレットまたはスマートフォンへ配信する。注文端末から中継サーバーへの実通信は行わない。

注文端末から中継サーバーへの通信は、別紙の[注文端末―中継サーバー通信仕様](./注文端末_中継サーバー通信仕様.md)に定義する。

## 2. 対象範囲

### 2.1 本書に含めるもの

- デシャップ画面のHTTPS配信
- 注文配信用WebSocketへの接続
- 接続時の初期スナップショット
- 注文追加・更新・取消の差分イベント
- イベントの順序管理
- 中継サーバー再起動の検出
- Ping/Pongによる死活確認
- Wi-Fi切断および端末スリープ後の再接続
- 再接続時の注文状態復旧
- 今回使用するモック注文シナリオ

### 2.2 本書に含めないもの

- 注文端末から中継サーバーへの注文登録
- 注文端末側の再送キュー
- 画面映像のWebRTC・VNC・動画配信
- 商品マスターの管理
- 決済処理
- インターネット経由での外部公開

## 3. 通信構成

```text
中継サーバーPC
  ├─ HTTPSでデシャップ画面を配信
  │      GET /kds
  │
  ├─ 注文状態をメモリに保持
  │
  └─ WebSocketで注文イベントを配信
         WSS /ws/orders
                  │
                  │ 店内Wi-Fi
                  ▼
         デシャップモニター
         タブレットのブラウザー
```

デシャップモニターは、最初にHTTPSで画面を開く。

```text
https://<中継サーバーのホスト名>/kds
```

画面内のJavaScriptは、同じ中継サーバーのWebSocketへ接続する。

```text
wss://<中継サーバーのホスト名>/ws/orders
```

検証環境でポートを明示する場合の例を次に示す。

```text
https://192.168.1.50:8443/kds
wss://192.168.1.50:8443/ws/orders
```

HTTPSで開いた画面からは、暗号化されていない`ws://`ではなく`wss://`へ接続する。本番想定ではTLS対応リバースプロキシでHTTPSとWSSを終端し、Node.jsの中継サーバーはPC内のループバックアドレスで待ち受ける構成を想定する。

## 4. 現行実装との差異

現行のデシャップ画面は、`GET /api/orders`を2秒間隔で取得するHTTPポーリング方式で注文を反映する。取得に失敗した場合は直前の表示を維持する。

本書で定義するWebSocket配信は現時点では未実装であり、次の機能を新たに追加する必要がある。

- `/ws/orders`のWebSocket接続口
- 接続中クライアントの管理
- 接続時の初期スナップショット送信
- 注文状態変更時の差分配信
- デシャップ画面側のWebSocketクライアント
- 再接続と再同期
- `sessionId`と`sequence`による順序管理
- Ping/Pongによる死活確認

移行期間中は、WebSocketを通常経路、`GET /api/orders`を復旧用またはフォールバック経路として残すこともできる。

## 5. 接続から表示までの流れ

```text
1. 中継サーバーを起動する
2. 中継サーバーがモック注文をメモリへ読み込む
3. デシャップモニターがHTTPSで画面を開く
4. 画面がWebSocketへ接続する
5. 中継サーバーが現在の注文を全件送信する
6. デシャップモニターが注文カードを描画する
7. 以後は追加・更新・取消だけを差分配信する
8. 切断時はデシャップモニターが再接続する
9. 再接続後、中継サーバーが最新状態を全件送信する
```

WebSocketは接続中に発生したメッセージのみを受信するため、接続前や切断中に発生した注文は差分イベントだけでは復元できない。そのため、初回接続および再接続時には必ず最新の全注文をスナップショットとして送信する。

## 6. 共通メッセージ形式

中継サーバーから送信するメッセージには、原則として次の共通フィールドを含める。

| フィールド | 内容 |
|---|---|
| `type` | メッセージ種別 |
| `sessionId` | 中継サーバープロセスの起動識別子 |
| `sequence` | 注文状態変更ごとに増加する連番 |
| `sentAt` | 中継サーバーが送信した日時。ISO 8601形式 |

```json
{
  "type": "order.created",
  "sessionId": "relay-20260830-001",
  "sequence": 11,
  "sentAt": "2026-08-30T18:00:05+09:00"
}
```

## 7. 初期スナップショット

WebSocket接続直後、中継サーバーは現在保持している注文をすべて送信する。

```json
{
  "type": "orders.snapshot",
  "sessionId": "relay-20260830-001",
  "sequence": 10,
  "sentAt": "2026-08-30T18:00:00+09:00",
  "orders": [
    {
      "orderId": "mock-001",
      "table": "12",
      "status": "new",
      "orderedAt": "2026-08-30T17:58:00+09:00",
      "people": 3,
      "items": [
        {
          "name": "土鍋御膳",
          "qty": 2,
          "note": "塩少なめ",
          "allergies": null,
          "done": false
        }
      ]
    }
  ]
}
```

デシャップモニターは、受信した`orders`を中継サーバー由来注文の正本として扱い、画面上のサーバー由来注文を置き換える。

デシャップ画面内で生成したローカル注文や、調理完了など端末固有の表示状態を維持する必要がある場合は、サーバー由来注文と別の状態として管理する。

## 8. 注文追加イベント

中継サーバー内で新しい注文を保持した後、接続中のデシャップモニターへ`order.created`を配信する。

```json
{
  "type": "order.created",
  "sessionId": "relay-20260830-001",
  "sequence": 11,
  "sentAt": "2026-08-30T18:00:05+09:00",
  "order": {
    "orderId": "mock-002",
    "table": "5",
    "status": "new",
    "orderedAt": "2026-08-30T18:00:05+09:00",
    "people": 2,
    "items": [
      {
        "name": "ウーロン茶",
        "qty": 2,
        "note": null,
        "allergies": null,
        "done": false
      }
    ]
  }
}
```

デシャップモニターは`orderId`をキーとして注文カードを追加する。同じ`orderId`がすでに存在する場合はカードを増やさず、受信した注文の内容で置き換える。

## 9. 注文更新イベント

数量、注記、注文状態などが変わった場合は、`order.updated`として更新後の注文全体を送信する。

```json
{
  "type": "order.updated",
  "sessionId": "relay-20260830-001",
  "sequence": 12,
  "sentAt": "2026-08-30T18:00:10+09:00",
  "order": {
    "orderId": "mock-002",
    "table": "5",
    "status": "new",
    "orderedAt": "2026-08-30T18:00:05+09:00",
    "people": 2,
    "items": [
      {
        "name": "ウーロン茶",
        "qty": 3,
        "note": "氷なし",
        "allergies": null,
        "done": false
      }
    ]
  }
}
```

部分フィールドだけを送るのではなく、更新後の注文全体を送る。これにより、デシャップモニター側のマージ処理を単純にし、更新の一部だけを取りこぼすことを防ぐ。

## 10. 注文取消イベント

注文取消時は、対象の`orderId`を`order.cancelled`として送信する。

```json
{
  "type": "order.cancelled",
  "sessionId": "relay-20260830-001",
  "sequence": 13,
  "sentAt": "2026-08-30T18:00:15+09:00",
  "orderId": "mock-002"
}
```

デシャップモニターは対象の注文カードを取消状態へ変更する。取消を即座に画面から消すか、一定時間「取消」として残すかは画面仕様で決定する。厨房での見落とし防止を考慮し、今回の検証では取消表示を一定時間残す方式を推奨する。

## 11. サーバー側の状態変更と配信順序

中継サーバーは、注文状態を変更してからWebSocketイベントを配信する。

```text
1. 中継サーバー内の注文状態を変更する
2. sequenceを1増やす
3. 差分イベントを作成する
4. 接続中のデシャップモニターへ配信する
```

配信してから状態を変更すると、配信直後に再接続した端末が古いスナップショットを受け取る可能性があるため、この順序を逆にしてはならない。

接続中クライアントへの送信に失敗しても、サーバー内の注文状態は維持する。失敗したクライアントは接続を閉じ、クライアント側の再接続後に最新スナップショットで復旧させる。

## 12. `sessionId`と`sequence`

### 12.1 `sessionId`

`sessionId`は中継サーバープロセスを起動するたびに新しく生成する。

デシャップモニターが以前と異なる`sessionId`を受信した場合は、中継サーバーが再起動したと判断し、以前の`sequence`を破棄して新しいスナップショットを正とする。

### 12.2 `sequence`

`sequence`は、注文状態が変化するたびに1ずつ増やす。同じ`sessionId`内では単調増加させる。

デシャップモニターは、すでに適用済みの番号以下のイベントを無視する。

```javascript
if (
  message.sessionId === currentSessionId &&
  message.sequence <= lastSequence
) {
  return;
}
```

受信した`sequence`が直前の番号より2以上進んでいる場合は、差分イベントを取りこぼした可能性がある。この場合はWebSocketを再接続するか、`GET /api/orders`でスナップショットを再取得する。

## 13. 通信断と再接続

デシャップモニターは、Wi-Fi切断、端末スリープ、ブラウザーのバックグラウンド化などによりWebSocketが切断する可能性がある。

切断を検出した場合は、次のように処理する。

```text
1. 現在表示している注文を消さない
2. 画面に「再接続中」と表示する
3. 1秒後に再接続する
4. 失敗時は2秒、4秒、8秒と待機時間を延ばす
5. 待機時間は最大30秒とする
6. 接続成功後に初期スナップショットを受信する
7. サーバー由来注文を最新状態へ置き換える
8. 接続状態を「接続済み」へ戻す
```

再接続処理の概略を次に示す。

```javascript
let retryCount = 0;

function connect() {
  const protocol = location.protocol === "https:" ? "wss:" : "ws:";
  const socket = new WebSocket(
    `${protocol}//${location.host}/ws/orders`
  );

  socket.addEventListener("open", () => {
    retryCount = 0;
    showConnectionStatus("connected");
  });

  socket.addEventListener("message", (event) => {
    const message = JSON.parse(event.data);
    applyOrderMessage(message);
  });

  socket.addEventListener("close", () => {
    showConnectionStatus("reconnecting");

    const delay = Math.min(
      1000 * Math.pow(2, retryCount),
      30000
    );

    retryCount += 1;
    setTimeout(connect, delay);
  });
}
```

## 14. Ping/Pongによる死活確認

注文イベントが長時間発生しない場合でも切断を検出できるよう、中継サーバーはWebSocketのPing/Pongを使用する。

```text
1. 中継サーバーが一定間隔でPingを送る
2. 接続中のブラウザーがPongを返す
3. 次回確認までにPongがない接続を切断する
4. デシャップモニターがcloseを検出して再接続する
```

ブラウザーのWebSocket APIはプロトコルレベルのPing/PongをJavaScriptから直接操作しない。Ping/Pongの管理は中継サーバー側のWebSocketライブラリで行う。

画面上でも最終受信時刻を表示する必要がある場合は、補助的にJSONのハートビートを送信できる。

```json
{
  "type": "heartbeat",
  "sessionId": "relay-20260830-001",
  "sequence": 13,
  "sentAt": "2026-08-30T18:01:00+09:00"
}
```

ハートビートでは`sequence`を増やさない。`sequence`は注文状態が変化した場合だけ増やす。

## 15. 受信確認

デシャップモニターからアプリケーションレベルの受信確認を返す場合は、次の形式とする。

```json
{
  "type": "orders.ack",
  "sessionId": "relay-20260830-001",
  "sequence": 13
}
```

今回の検証では、中継サーバーが差分イベント履歴を永続保存しないため、ACKがない個別イベントを再送するキューは設けない。

受信保証は次の方針とする。

- 接続中は差分イベントを即時配信する
- 切断時はデシャップモニターの直前表示を維持する
- 再接続時は最新スナップショットを全件送信する
- ACKは接続状況の監視およびログ確認に使用する
- 差分イベントの欠落はスナップショットで解消する

## 16. 認証とセキュリティ

- デシャップ画面とWebSocketは同一オリジンで提供する。
- 本番ではHTTPSおよびWSSを使用する。
- WebSocket接続時に`Origin`を検証し、許可した画面からの接続だけを受け付ける。
- 認証情報の実値をURLクエリ、ログ、リポジトリへ保存しない。
- ブラウザーからWebSocketへ任意の`Authorization`ヘッダーを設定できないため、HTTPS画面へのログイン後に発行したSecureかつHttpOnlyなCookieをWebSocket接続でも確認する方式を推奨する。
- 中継サーバーは店内のプライベートネットワークからのみ到達可能にする。
- ゲストWi-Fiなど、来店客用ネットワークから接続できないよう分離する。
- 受信メッセージのサイズ上限、接続数上限、アイドルタイムアウトを設定する。

今回の閉じた検証環境で一時的に簡易認証を使用する場合でも、秘密情報をソースコードへ直接記載しない。

## 17. モック注文シナリオ

ストリーミングを目視確認するため、中継サーバー起動後に時間差で注文状態を変更する。

```text
起動直後：mock-001、mock-002を初期状態として保持
5秒後   ：mock-003を追加
10秒後  ：mock-001の数量を更新
15秒後  ：mock-002を取消
```

各タイミングで送信するイベントを次に示す。

| タイミング | サーバー内の処理 | 配信イベント |
|---|---|---|
| WebSocket接続時 | 現在の注文を全件取得 | `orders.snapshot` |
| 5秒後 | `mock-003`を追加 | `order.created` |
| 10秒後 | `mock-001`を更新 | `order.updated` |
| 15秒後 | `mock-002`を取消 | `order.cancelled` |
| 再接続時 | 最新の注文を全件取得 | `orders.snapshot` |

モック注文は、本番の注文登録APIで正規化された後と同じデータ形式にする。これにより、将来注文端末を接続した場合も、中継サーバーからデシャップモニターへの配信処理を共通利用できる。

## 18. 障害試験

### 18.1 Wi-Fi切断

1. デシャップモニターへ初期注文が表示されていることを確認する。
2. タブレットのWi-Fiを無効にする。
3. 直前の注文表示が消えないことを確認する。
4. 「再接続中」が表示されることを確認する。
5. Wi-Fiを有効にする。
6. WebSocketが自動再接続することを確認する。
7. 最新スナップショットによって注文状態が復旧することを確認する。

### 18.2 中継サーバー再起動

1. デシャップモニターを接続した状態で中継サーバーを停止する。
2. デシャップモニターが切断を検出することを確認する。
3. 中継サーバーを再起動する。
4. 新しい`sessionId`が生成されることを確認する。
5. デシャップモニターが再接続することを確認する。
6. 新しいスナップショットで表示が置き換わることを確認する。

### 18.3 端末スリープ

1. デシャップ画面を表示した状態でタブレットをスリープさせる。
2. スリープ中にモック注文を追加する。
3. タブレットを復帰させる。
4. WebSocketが再接続することを確認する。
5. スリープ中に追加された注文がスナップショットから表示されることを確認する。

### 18.4 複数端末

1. 複数のタブレットまたはブラウザーから接続する。
2. すべての端末が同じ初期スナップショットを受信することを確認する。
3. モック注文を追加・更新・取消する。
4. すべての端末へ同じ`sequence`のイベントが配信されることを確認する。

## 19. 実装方針

Node.jsの中継サーバーでは、WebSocketライブラリを既存HTTPサーバーのUpgrade処理へ接続し、`/ws/orders`だけをWebSocketとして受け付ける構成を想定する。

実装に必要な主な要素を次に示す。

- WebSocketライブラリ
- WebSocket接続口 `/ws/orders`
- 接続クライアントの集合
- 注文状態を保持する既存の`Map`
- 起動単位の`sessionId`
- 状態変更単位の`sequence`
- スナップショット生成処理
- 全接続へのブロードキャスト処理
- Ping/Pongによる接続確認
- モック注文の読込および時間差シナリオ
- デシャップ画面側の接続・再接続・イベント適用処理
- HTTPS／WSSを終端するリバースプロキシ

WebSocketクライアントごとのイベント履歴や個別再送キューは今回の範囲に含めない。切断復旧は最新スナップショットの再送で行う。

## 20. 通信責務

| 通信 | 方式 | 目的 |
|---|---|---|
| デシャップ画面の取得 | HTTPS | HTML、CSS、JavaScriptを読み込む |
| 初期注文一覧 | WebSocket | 接続・再接続時に現在の注文状態を同期する |
| 注文追加 | WebSocket | 新しい注文をリアルタイム表示する |
| 注文更新 | WebSocket | 注文内容または状態の変更を反映する |
| 注文取消 | WebSocket | 取消状態を反映する |
| 死活確認 | WebSocket Ping/Pong | 切断した接続を検出する |
| 復旧 | WebSocket再接続＋スナップショット | 切断中の取りこぼしを解消する |
| フォールバック | HTTPS `GET /api/orders` | WebSocket利用不能時に最新状態を取得する |

## 21. 受け入れ条件

- 実タブレットからWSSへ接続できる。
- 接続直後に初期モック注文が表示される。
- モック注文の追加がポーリング待ちなしで表示される。
- モック注文の更新が同じカードへ反映される。
- モック注文の取消が指定した表示方法で反映される。
- 同じ`orderId`のカードが重複して増えない。
- 古い`sequence`のイベントが画面へ再適用されない。
- Wi-Fi切断中も直前の注文表示が維持される。
- Wi-Fi復旧後に自動再接続する。
- 再接続後のスナップショットで最新状態へ復旧する。
- 中継サーバー再起動後、新しい`sessionId`の状態を取り込める。
- 端末スリープからの復帰後に最新状態へ同期できる。
- 複数のデシャップモニターへ同じ注文状態を配信できる。
