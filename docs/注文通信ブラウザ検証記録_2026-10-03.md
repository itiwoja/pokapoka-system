### 検証ハーネスの構成と制約

- 現行 relay の静的配信は許可リスト制で、検証画面を置いただけでは配信されない（製品コードは変更しない方針）。そのため `tests/browser/order-comm/harness-proxy.js` が同一origin（スキーム・ホスト・ポート共通）の前段として `/harness`（検証画面）と `/order-client.js`（検証対象 clone の実ファイル）を配信し、それ以外は実 relay へそのまま中継する。
- 通信障害（切断、応答喪失、遅延、任意の HTTP ステータス、不正な受付応答）は、この前段が `POST /api/orders` にだけ注入する。relay 側の受付件数・重複判定は relay 自身の応答（201 / `duplicate: true`）と `GET /api/orders` で確認した。
- IndexedDB の保存失敗は、検証画面側で `IDBObjectStore.add/put` と `IDBFactory.open` を差し替えて再現した（transaction の abort、`QuotaExceededError` の送出、open の失敗）。実際の容量超過・ストレージ破損・プライベートモードではない（§6）。
- 30分の期限超過は、検証画面から `order-client` へ渡す `now()` に `window.__skew` を足して時計を進めた（ブラウザ側モック）。OS時計は変更していない。
- 検証画面のカート・二重タップ防止は `docs/注文端末_通信モジュール組み込み.md` の組み込み例に沿った最小実装であり、実注文画面への組み込み合格ではない。
- スクリーンショットの日本語が豆腐表示なのは、この環境に日本語フォントが無いため。判定は DOM のテキストで行っており、表示の見た目は検証対象外。

## 7. 新規の不具合・観察

新規の不具合は見つからなかった。Issue 化が必要な項目はない。以下は不具合ではない観察。

1. **Chromium が接続断・408 の POST を内部で再試行する（推測）。** 接続断を1回だけ注入すると、`order-client` に失敗が見えないまま同じ POST がもう1回送られた（ブラウザの fetch 発行数 < relay 手前の POST 数。408 を返し続けた A250-4-408 でも fetch 4回に対し POST 7回）。`order-client` は同じ注文IDで冪等に再送する設計のため、relay は重複受付せず問題はない。ただし画面側で「`retryCount`＝実際の送信回数」とは扱えない。ブラウザ内部の挙動は推測であり、確証は取っていない。
2. **`needs_review` からの復帰手段が `order-client` に無い。** `retry()` は `failed` 専用で、`needs_review` は拒否される（現行仕様どおり）。スタッフが照合した後に画面から記録を整理する方法は未定義。実機運用の前に決める事項として #240 作業3・#198 で扱うのが妥当（推測）。
3. **環境変数 `RELAY_TRUST_LOOPBACK` は値 `0` でのみループバック免除を無効にする。** 環境変数に `false` を渡しても無効にならず、認証が効いたように見えて素通りする（本検証でも最初に誤設定した）。`config.json` の真偽値 `false` は `load-config.js` が `"0"` へ変換するため、設定ファイル経由では問題ない（コードで確認）。環境変数で直接指定する検証手順では `0` を使う。
