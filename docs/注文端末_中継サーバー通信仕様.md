# 注文端末―中継サーバー通信仕様

## 1. 目的

本書は、注文端末から店内の中継サーバーへ注文データを送信する際の通信方式、API契約、受信確認、再送、通信断からの復旧方法を定義する。

今回のデシャップ配信検証では、注文端末から中継サーバーへの実通信は行わない。中継サーバー内で生成したモック注文を使用する。本書の内容は、将来注文端末を接続する際の通信契約として扱う。

## 2. 対象範囲

### 2.1 本書に含めるもの

- 注文端末から中継サーバーへの注文登録
- 中継サーバーから注文端末への受信確認
- タイムアウトおよび通信断時の再送
- 同一注文の二重登録防止
- 注文取消
- 認証およびHTTPS利用時の基本方針
- 今回のモック検証との対応関係

### 2.2 本書に含めないもの

- 中継サーバーからデシャップモニターへのWebSocket配信の詳細
- デシャップモニター上の表示・調理完了操作
- 商品マスターの管理方法
- 決済処理
- TableCheckとの予約同期

## 3. 全体構成

本番接続では、注文端末はHTTPSで中継サーバーへ注文を送信する。中継サーバーは注文を受け付けた後、別のWebSocket接続を使ってデシャップモニターへ通知する。

```text
注文端末
   │
   │ HTTPS（注文登録・取消・受信確認）
   ▼
中継サーバー
   │
   │ WebSocket（初期スナップショット・差分イベント）
   ▼
デシャップモニター
```

注文端末から中継サーバーへの通信にはHTTPSを使用する。WebSocketは、中継サーバーからデシャップモニターへのリアルタイム通知に使用し、注文登録の必須経路にはしない。

## 4. 通信先

本番想定の接続先は次のとおりとする。

```text
https://<中継サーバーのホスト名>/api/orders
```

検証環境でポートを明示する場合の例を次に示す。

```text
https://192.168.1.50:8443/api/orders
```

現行の中継サーバー実装はHTTPで待ち受けているため、HTTPS化する場合はTLS対応リバースプロキシまたは中継サーバー自体のHTTPS対応が必要である。店内LANであっても、認証情報と注文内容の平文送信を避けるため、本番運用ではHTTPSを使用する。

## 5. 注文登録API

### 5.1 リクエスト

```http
POST /api/orders
Content-Type: application/json
Authorization: Bearer <端末用トークン>
```

```json
{
  "orderId": "t12-20260830-0001",
  "table": "12",
  "people": 4,
  "orderedAt": "2026-08-30T18:05:00+09:00",
  "items": [
    {
      "name": "山城牛の肉たく土鍋御膳",
      "qty": 2,
      "note": "塩少なめ"
    },
    {
      "name": "ウーロン茶",
      "qty": 4
    }
  ]
}
```

### 5.2 フィールド

| フィールド | 必須 | 内容 |
|---|---:|---|
| `orderId` | 必須 | 注文端末が生成する一意な注文ID。64文字以内。同じ注文の再送では変更しない |
| `table` | 必須 | 卓番。6文字以内。送信元IPではなくペイロードに含める |
| `people` | 任意 | 人数。0～99 |
| `orderedAt` | 任意 | ISO 8601形式の注文日時。省略時は中継サーバーの受信時刻を使用する |
| `items` | 必須 | 注文明細の配列。1件以上 |
| `items[].name` | 必須 | 品名。80文字以内 |
| `items[].qty` | 任意 | 数量。1～99。省略時は1 |
| `items[].note` | 任意 | 品目の注記。200文字以内 |
| `items[].allergies` | 任意 | アレルギー注記。200文字以内 |

`orderedAt`が中継サーバーの現在時刻より未来になっている場合、現行実装は中継サーバーの時刻へ丸める。これは注文端末の時計ずれによって、デシャップ画面の経過時間が不正になることを防ぐためである。

### 5.3 成功応答

新しい注文を受け付けた場合は、`201 Created`を返す。

```http
HTTP/1.1 201 Created
Content-Type: application/json
```

```json
{
  "ok": true,
  "duplicate": false,
  "order": {
    "id": "t12-20260830-0001",
    "table": "12",
    "type": "new"
  }
}
```

注文端末は、この成功応答をアプリケーション上の受信確認（ACK）として扱う。成功応答を受け取るまで、注文を端末内の未確認キューから削除してはならない。

### 5.4 重複再送への応答

同じ`orderId`がすでに登録されている場合は、二重登録せず`200 OK`を返す。

```json
{
  "ok": true,
  "duplicate": true,
  "order": {
    "id": "t12-20260830-0001",
    "table": "12",
    "type": "new"
  }
}
```

`duplicate: true`も受付済みを示す正常応答である。注文端末は対象注文を送信済みとして扱う。

同じ`orderId`で異なる内容を送信しても、現行中継サーバーは最初に受け付けた内容を正とし、後から送られた内容では上書きしない。内容を変更する場合のAPIは別途定義が必要である。

### 5.5 エラー応答

| 状況 | HTTPステータス | 注文端末の動作 |
|---|---:|---|
| 入力値が不正 | `400 Bad Request` | 自動再送しない。入力内容または端末実装を確認する |
| 認証情報がない・不正 | `401 Unauthorized` | 自動再送を停止し、端末設定を確認する |
| 許可されていない操作 | `403 Forbidden` | 自動再送を停止し、権限設定を確認する |
| 対象注文が存在しない | `404 Not Found` | 操作内容に応じて端末状態を再同期する |
| サーバー内部エラー | `500 Internal Server Error` | 間隔を空けて再送する |
| 応答なし・タイムアウト | 応答なし | 同じ`orderId`で再送する |

## 6. 注文取消API

注文取消には注文登録時と同じ`orderId`を使用する。

```http
DELETE /api/orders/t12-20260830-0001
Authorization: Bearer <端末用トークン>
```

| 結果 | HTTPステータス | 内容 |
|---|---:|---|
| 取消成功 | `204 No Content` | 注文を中継サーバーから削除した |
| 対象なし | `404 Not Found` | 指定した`orderId`が存在しない |

取消要求についても通信断時の結果不明を考慮する必要がある。取消の再送時に`404`となった場合、それが「すでに取消済み」なのか「最初から存在しない」のかは現行APIだけでは区別できない。厳密な取消確認が必要な場合は、取消済み状態を保持して冪等な成功応答を返す仕様への拡張を検討する。

## 7. 注文更新

現行中継サーバーには、登録済み注文の内容を更新するAPIはない。同じ`orderId`を`POST /api/orders`で再送しても内容は更新されない。

本番で数量変更、品目追加、注記変更などが必要な場合は、次のいずれかを別途決定する。

- `PUT /api/orders/{orderId}`で注文全体を置換する
- `PATCH /api/orders/{orderId}`で一部項目を変更する
- 変更後の注文を新しい`orderId`で追加し、元注文を取り消す

更新競合を防ぐ場合は、注文に`version`を持たせ、中継サーバーが期待するバージョンと一致した場合だけ更新する方式が望ましい。更新方式は現時点では未確定とする。

## 8. 再送と二重登録防止

### 8.1 基本原則

注文端末は、注文をネットワークへ送信する前に端末内の永続領域へ保存する。ブラウザーを注文端末として使用する場合は、IndexedDBなどを使用する。

最低限、次の情報を保持する。

```json
{
  "orderId": "t12-20260830-0001",
  "status": "pending",
  "retryCount": 0,
  "createdAt": "2026-08-30T18:05:00+09:00",
  "lastAttemptAt": null,
  "payload": {
    "table": "12",
    "items": [
      {
        "name": "山城牛の肉たく土鍋御膳",
        "qty": 2
      }
    ]
  }
}
```

### 8.2 結果不明時の再送

次のように、サーバーが登録を完了した後に通信が切れる場合がある。

```text
注文端末                     中継サーバー
   │ POST /api/orders             │
   ├─────────────────────────────▶│
   │                         注文を登録
   │                         201を送信
   │          × 通信断             │
   │  成功応答を受信できない        │
   │                               │
   │ 同じorderIdで再送              │
   ├─────────────────────────────▶│
   │◀──────── 200 duplicate:true ─┤
```

注文端末は、タイムアウト時に新しい`orderId`を発行してはならない。同じ`orderId`を使用することで、中継サーバーが重複を検出できる。

### 8.3 再送間隔

サーバーへ到達できない場合は、短時間に連続送信せず、待機時間を段階的に延ばす。

```text
1回目: 1秒後
2回目: 2秒後
3回目: 4秒後
4回目: 8秒後
以降 : 最大30秒間隔
```

端末がオンラインへ復帰したことを検知した場合は、未確認キューの送信を再開する。ただし、複数注文を同時に大量送信せず、受付結果を確認しながら順番に処理する。

## 9. 注文端末側の状態

注文端末は各注文を次の状態で管理する。

| 状態 | 内容 |
|---|---|
| `pending` | 端末内へ保存済みで、まだ送信していない |
| `sending` | 中継サーバーへ送信中 |
| `accepted` | `201`または`200 duplicate:true`を受信した |
| `retry_wait` | 通信エラーが発生し、再送を待っている |
| `rejected` | `400`など、内容修正が必要なエラーを受信した |

画面上では、少なくとも「送信中」「送信済み」「送信できていない」を利用者が区別できるようにする。

## 10. 認証とネットワーク

- 注文端末と中継サーバーは同じ店内LANへ接続する。
- 注文端末ごと、または店舗単位で推測困難な認証トークンを設定する。
- トークンの実値をリポジトリ、ログ、画面、サンプル設定へ保存しない。
- 本番ではHTTPSを使用し、端末が信頼できる証明書を設定する。
- 中継サーバーのポートは店内のプライベートネットワークからのみ到達可能にする。
- ゲストWi-Fiなど、来店客が利用するネットワークから中継サーバーへ到達できないよう分離する。
- 卓番はIPアドレスから決定せず、注文ペイロードの`table`を使用する。

## 11. 中継サーバー受信後の処理順序

中継サーバーは次の順番で処理する。

```text
1. HTTPSリクエストを受信
2. 認証を確認
3. JSON形式と各フィールドを検証
4. orderIdの重複を確認
5. 新規注文を保存
6. 注文端末へ成功応答を返す
7. デシャップモニターへWebSocketイベントを配信
```

注文の保存に失敗した場合は、デシャップモニターへイベントを配信しない。これにより、デシャップ画面には表示されたが中継サーバーには存在しない、という不整合を防ぐ。

## 12. 今回のモック検証との関係

今回の検証では、注文端末と中継サーバー間のHTTPS通信を実行しない。中継サーバー内部のモック生成処理が注文端末の代わりに注文状態を作成する。

```text
本番構成
注文端末 ── HTTPS ──▶ 中継サーバー ── WebSocket ──▶ デシャップモニター

今回の構成
モック生成処理 ── 内部投入 ──▶ 中継サーバー ── WebSocket ──▶ デシャップモニター
```

モック注文も、本番の`POST /api/orders`で正規化された後と同じ注文データ形式にする。これにより、将来注文端末を接続しても、中継サーバーからデシャップモニターへの配信処理を変更せず利用できる。

## 13. 現行実装と今後の決定事項

### 13.1 現行実装で利用できるもの

- `POST /api/orders`による注文登録
- `GET /api/orders`による当日注文フィード取得
- `DELETE /api/orders/{orderId}`による取消
- 同じ`orderId`の重複登録防止
- 新規登録時の`201`応答
- 重複再送時の`200`および`duplicate: true`応答
- 入力値検証
- TTLによる期限切れ注文の除去

### 13.2 現時点で未実装または未確定のもの

- 注文端末から中継サーバーまでのHTTPS終端
- 注文端末の永続的な未確認キュー
- 注文更新API
- 取消要求の完全な冪等化
- 商品を名前で識別するか商品IDで識別するか
- 中継サーバー再起動後も注文を保持するか
- デシャップ完了済み注文を中継サーバーへ反映するか

現行中継サーバーは注文をプロセス内のメモリに保持する。中継サーバーを再起動すると受付済み注文は消えるため、本番で再起動後の復元が必要な場合は、注文端末からの再送または中継サーバー側の永続保存を追加する。
