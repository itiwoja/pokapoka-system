# チビ伝 実機印刷: プリンターは ESC/POS ではなく STAR Line Mode（2026-07-31 実機検証）

> 実機（Star mC-Print3 MCP31LB WT JP）へ有線LAN経由で4枚印字して判明したこと。
> 関連: Issue #144 / PR #148・#166 / 2026-07-17 のレシートプリンターのネットワーク接続検討

## 結論

**mC-Print3 の出荷時エミュレーションは STAR Line Mode で、ESC/POS ではない。**
PR #148 / #166 の `relay-server/printer.js` は ESC/POS のつもりで組み立てていたため、
制御コマンドが一つも効いていなかった。

## 何が起きていたか（1枚目の実物）

```
@                  ← ESC @ の "@" がそのまま印字
土鍋飯ぽかぽか      ← 中央寄せされない
!卓  A1            ← GS ! の "!" が漏れる。倍角にならない
!受付 10:15
```

- ESC/POS の中央寄せ `ESC a 1`(1B 61 01) は、**STAR Line Mode では「1行紙送り」**。
  だから中央寄せされず余計な改行だけ入った
- ESC/POS の文字サイズ `GS !`(1D 21 n) は STAR に存在しない。`GS` だけ消費されて `!` が印字された
- 末尾の `ESC d 5`（紙送りのつもり）は、**STAR では `ESC d n` がオートカッター**で定義域 0〜3。
  5 は範囲外で無視され、続く `ESC d 2` が偶然フルカットを実行していた

**Why:** エミュレーションが違うと、解釈できないバイトは**エラーにならずそのまま文字として印字される**。
relay-server は送信成功として `{"ok":true}` を返し、KDS 側も成功扱いになる。
つまり **完全に壊れていても誰も異常に気づけない**。今回も「紙は出た」で見逃しかけた。

**How to apply:** 実機印字の検証は「送信が成功したか」ではなく**必ず現物の紙を見る**。
自動テストで担保できるのはバイト列までで、そのバイト列が正しい体系かは実機でしか分からない。

## 採用した方針: コード側を STAR ネイティブへ

選択肢は2つあった。

| | 内容 | 判断 |
|---|---|---|
| A | プリンターを ESC/POS エミュレーションに切り替える | 不採用 |
| B | `printer.js` を STAR Line Mode コマンドで書き直す | **採用** |

**Why:** A はコード変更ゼロで直せるが、正しい印字が「プリンター側の隠れた設定」に依存する。
上記のとおり設定が違っても無言で壊れるだけなので、買い足し・故障交換・初期化のたびに
誰かがメモリスイッチを覚えていないと同じ壊れ方が再発し、しかも気づけない。
**出荷状態のまま挿せば正しく出る**状態にしておく方が店舗システムとして安全と判断した。
代償は Star 機前提になること。

**How to apply:** 将来ラスター印刷（自由レイアウト）へ進む場合も、
ラスター転送コマンドは ESC/POS と STAR で別物なので、同じ判断がそのまま効く。

## 使用コマンド（STAR Line Mode Command Specifications Rev.1.80）

| 目的 | コマンド | Hex |
|---|---|---|
| 左寄せ / 中央寄せ | `ESC GS a n` | `1B 1D 61 00` / `1B 1D 61 01` |
| 拡大（n1=縦, n2=横。0=等倍, 1=2倍） | `ESC i n1 n2` | `1B 69 n1 n2` |
| 強調 ON / OFF | `ESC E` / `ESC F` | `1B 45` / `1B 46` |
| n行紙送り（1≤n≤127） | `ESC a n` | `1B 61 n` |
| カット位置まで送って部分カット | `ESC d 3` | `1B 64 03` |

出典: STAR Line Mode Command Specifications Rev.1.80
（https://www.starmicronics.com/support/Mannualfolder/starline_cm_en.pdf）

### 初期化コマンド `ESC @` は使わない

**Why:** 仕様書には載っているが、**mC-Print3 実機では解釈されず `@` が伝票の1行目に印字された**（3枚目で確認）。
中央寄せ `ESC GS a` は効いているので `ESC` 自体は正しく処理されており、`ESC @` 固有の挙動。

**How to apply:** 代わりに、このモジュールが触る属性（寄せ・拡大・強調）を先頭で明示的に既定へ戻す
（`ESC GS a 0` + `ESC i 0 0` + `ESC F` の10バイト）。触る属性が3つだけなので開始状態はこれで確定する。

## ネットワーク構成（2026-07-31 の検証環境）

- プリンターは**有線LAN**で接続。`192.168.244.41` の 9100番ポート
- 2026-07-17 に持ち越していた「MCW10 無線アダプターの有無」は、**有線接続を選んだため確認不要になった**
- 検証時は KDS サーバーが Wi-Fi 側（`10.108.0.75`）、プリンターが有線側（`192.168.244.x`）と
  **別セグメント**で、PC が両方に足を出している状態で疎通した

**未決定:** 店舗ではこの2つを同じLANに寄せるのか、ミニPCが両方に接続する構成にするのか。
プリンターのIPは固定（DHCP予約 or 静的）にしないと、変わった時点で印字できなくなる。

## 日本語（Shift_JIS）について

Shift_JIS 変換（`iconv-lite`）と漢字印字は**最初から正常に動いていた**。
1枚目で日本語が化けたのは Git Bash が `curl -d` の引数を壊していたためで、
`printer.js` 側の問題ではなかった（ソース直書きの「卓」「※」だけ化けずに出ていたのが手がかり）。

**How to apply:** コマンドラインから疎通確認する際、日本語を含む JSON は
シェル引数に直接埋め込まない。UTF-8 のファイルか Node スクリプト経由で送る。
