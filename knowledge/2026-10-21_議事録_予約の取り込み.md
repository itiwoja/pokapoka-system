## 決定事項

### 1. 予約は TableCheck から CSV で取り込む

- 2026-10-11 に API 連携をやめた後の、予約の主な入口を **CSV** にする（準備資料 2-2 の「B. CSV」）
- 詳細：[決定：予約のCSV取込と変更の反映](2026-10-21_決定_予約のCSV取込と変更の反映.md)

### 2. 予約に変更があったときは、CSV を再度取り込む

- 変わった予約を予約入力画面で手で直すのではなく、TableCheck から CSV を出し直して取り込み直す
- 今の試作は予約番号ごとに上書きするので、取り直しても壊れないための直しが要る（予約番号の列を必須にする、CSV から消えた予約の扱い、こちらで入れた卓番を上書きしない、など。決定の記録の「やること」）

### 3. 当日に、その日の予約を全部チェックする

- **当日の予約は無い**ので、当日にその日の予約を全部 CSV で取り込めば、前日までの新規・キャンセル・人数や時間の変更がすべて入る
- ⚠️ [2026-06-03 運用確認](2026-06-03_運用確認_電源充電・KDS台数.md) C の「当日予約が多々ある（当日電話予約／来店後に予約して戻る）」と食い違う。電話の当日予約も無いのか、TableCheck 経由の当日予約が無いという意味かを確かめる

## 店の運用で分かったこと

### 4. 新規予約とキャンセルは通知が来るが、人数・時間の変更は分からない

| 予約の動き | 通知 |
| :--- | :--- |
| 新規予約 | 来る |
| キャンセル | 来る |
| 人数・時間の変更 | 来ない（分からない） |

- 通知を見て「変わったから取り込み直す」ことはできない → 決定3（当日に全部チェック）で取りこぼさない

### 5. 外国人のお客様は、来店時に予約IDを見せてくる

- 予約IDが、来店時に予約を見つけるいちばん確かな手がかりになる
- CSV の予約番号は予約の ID として持てているが、KDS の予約ストックにも `/reservations` の一覧にも予約IDが出ず、探せない
- 詳細：[運用：外国人のお客様は予約IDを見せる](2026-10-21_運用_外国人のお客様は予約IDを見せる.md)

### 6. 当日はよく電話が鳴るので、中に入らない管理用の入力機器を1台置いたほうがいい

- 当日は電話がよく鳴る。電話を受けた人が中（厨房）に入らずに入力できるよう、**管理用の入力機器を1台**設けたほうがいい
- KDS の2台（厨房のコンロ側・ホール／中間。[2026-06-03 運用確認](2026-06-03_運用確認_電源充電・KDS台数.md) C）とは別の、**3台目**になる。置き場所は電話・レジの近くと読んだ（確かめる）
- この機器でしそうなこと（推測。確かめる）：電話で受けた予約・変更・キャンセルの入力（予約入力画面 `/reservations`）、当日の CSV の取り込み（決定3）、予約IDで予約を探す（事実5）
- ⚠️ 決定3の「当日の予約は無い」と合わせて、**当日の電話の中身**（当日の予約・変更・キャンセル・問い合わせのどれが多いか）を確かめる。当日の予約が電話で入るなら、予約の入口（#292）はこの機器になる
- 機器の調達（[機器調達提案書](../docs/機器調達提案書.md)）に1台足すことになる。予約の入口の画面の設計に入る前に確認が要る（CLAUDE.md）

## 次にやること

- 実物の CSV（その日の分、名前・電話・メールはダミー）をもらい、予約番号の列・取消の出方・人数の区分・コース名を確かめる（準備資料 2-3）
- CSV の取り直しで壊れないように直す（決定の記録の「やること」2〜5）
- 当日の取り込みの手順（誰が・何時に・どの端末で）を店と決める。最初の予約の「来店30分前」（炊飯準備の合図）より前に取り込む必要がある
- 予約IDを予約ストックと `/reservations` の一覧に出し、探せるようにする
- 当日の電話予約の有無を確かめ、あれば入口（#292）を決める
- 管理用の入力機器（3台目）の置き場所・機種・この機器でする作業を店と決め、機器調達に足す
