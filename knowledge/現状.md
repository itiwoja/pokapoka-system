## 現行実装

| 項目 | 状況・参照先 |
|---|---|
| KDS | `kds-a-grid.html`（HTML / CSS / JavaScript、ローカルJS・音声参照あり）。新規淡青／予約淡金、グリッド／レーン、コンロとタイマーの独立割当、品目完了数を管理。[画面仕様](../docs/deshup-spec.md) |
| 注文経路 | 別チームの注文端末 → 注文サーバー（3001番、PostgreSQL保存）→ relay（8000番）→ KDS。転送先 `RELAY_ORDERS_URL` の設定が必要。`requestId` は端末の再送キー、relayの `orderId` は注文サーバーの `Order.id`。[接続契約](../docs/注文端末_注文サーバー接続.md) |
| 予約入力 | `/reservations` に手入力・CSV／Excel（.xlsx）取込・貼り付け・メールの入口と、日付別一覧・変更・取消を試作済み。貼り付け・メールは下書きを人が確認してから登録。[手順・API](../relay-server/README.md#予約の保存reservation-storejs) |
| 予約保存・配信 | 店内分は `data/reservations.sqlite` に保存。大人・シニア・子供・幼児の4区分を持ち、当日の `booked` かつメニューありだけを `/api/stock` へ配信。ストック取得時に過去日を削除。TableCheckは元の予約を引き続き管理する |
| 注文配信・同期 | `/ws/orders` で即時注文配信し、切断中はHTTPで補完。厨房状態（コンロ・完了数・ロック・並び順・削除）はrelay経由で別端末へ共有。LocalStorage / BroadcastChannelだけでは別端末へ届かない |
| 同期の対象外 | 炊飯cue・厨房限定卓番上書き・提供準備完了cue・前菜／デザート提供確認・予約から着手したカードは別端末間では未共有。同一originタブ間の同期と区別する |
| 提供・印刷 | 全品完了は厨房では非表示、ホールではデザート提供まで保持。前菜／デザートの提供確認とチビ伝印刷はホール。プリンター未設定・送信失敗時はブラウザ印刷へフォールバック |
| 音 | 新着注文のししおどし音を実装済み（「通知音ON」が必要）。初回表示・同一ID再送では鳴らさない。10分超の遅延ビープはない |
| 保存範囲 | relayの注文・厨房状態・ローカル座席占有はメモリ。予約SQLite、監査ログ、印刷設定はファイル保存。別チームの注文サーバーの保存と混同しない。[データ配置](../docs/db-design.md#13-データ配置) |

## 最新の決定と未実装・未決

根拠は [2026-10-21 議事録](2026-10-21_議事録_予約の取り込み.md) と [予約CSV取込の決定](2026-10-21_決定_予約のCSV取込と変更の反映.md) です。

- **予約は朝1回当日分を確認・取り込み、変更時は再取込**。CSVが主な運用入口だが、受領した実ファイルはExcelで、現行コードは両方を読める。担当者・時刻・端末、取消が書き出しにどう載るかは未確認。
- **再取込の安全性は未完成**：予約番号を必須にしていない。番号が無いまま日時・名前が変わると重複し得る。ファイルから消えた予約は消さず、手修正した卓番・メモ・取消状態は上書きされ得る。
- **当日の電話予約は要確認**：6/3の「当日予約が多々ある」と10/21の「当日の予約は無い」の意味が食い違う。独断でどちらかに統一しない。
- **管理用入力機器をKDS2台とは別に1台置く案**：置き場所・機種・作業範囲は未決。既存 `/reservations` は試作で、正式な管理用画面の内容も未設計。
- **予約IDで探す運用**：ID取込はできるが、KDS予約カード・予約入力一覧での表示／検索は未実装。お客様が見せる番号との一致も確認待ち。
- **店内サーバーOSはLinux、技術スタックはNext.jsへ移行する方針**。ディストリビューション・保守担当・常駐／バックアップ手順、移行範囲・理由・時期は確認待ち。現行はNode HTTP＋HTMLで、移行・配備済みとは扱わない。
- KDSの運用判断（予約の着手主体、前菜を飛ばす例外、ドリンク、経過時間の閾値・明滅、アレルギーの見せ方、蒸らし）の最新会議での結論は未記録。
