#### Q1. 予約のお客様を「進行中」に移すのは、誰がいつ？（#291）

- 背景：6/4 にオーナーは「炊き始めた時点で進行中へ移す」と話した（[オーナー確認事項](2026-06-04_オーナー確認事項_準備メモ.md) D-2）。今の画面は「来店したときにホールが卓番を選んで『調理開始』を押す」になっていて、食い違っている。卓番は来店時に決まる（遅延割当）
- 選択肢
  - ア) 30分前に厨房が押す。卓番は「未定」のまま進行中へ出し、来店時にホールが卓番を入れる
  - イ) 今の形のまま。30分前は厨房が「炊飯準備」を確認するだけで、来店時にホールが卓番を選んで移す
- **推し：イ**。卓番が無いと前菜・チビ伝・卓番の付け替えがかみ合わない。「炊き始め」は炊飯準備の確認で表せる。ボタン名は「来店」などに変える
- こうだったらこう：アなら「卓番未定のカード」を作る（変更が大きい）
- 補足（こちらの問題）：今は移したカードが押した端末にしか出ず、再読み込みで消える。どちらの答えでも直す（#291）

#### Q2. 前菜を出さずにデザートへ進むことはある？（#289）

- 背景：提供順は前菜→膳→デザート（9/3）。今は前菜を出していない卓でも、デザートを長押しすると卓が閉じてしまう
- 聞き方：「子どもだけの卓など、前菜を出さない卓はありますか」
- 選択肢：案A 前菜を出すまでデザートを押せない／案B 確認を挟む／案C デザートを出したら前菜も出したことにする
- **推し：案A**。**下書きを作ってある**（ブランチ `feat/kds-dessert-after-starter`。前菜が未提供の卓は、デザートの帯に「先に前菜を出してください」と出る）
- こうだったらこう：前菜を出さない卓があるなら案B
- あわせて：ホールで前菜の「出した」を押し間違えたとき、今は取り消せない（#295）。取り消しが要るか

#### Q3. ドリンクは誰が作って、誰が運ぶ？（#295）

- 背景：今はドリンクも厨房の画面に品目として並ぶ。厨房が押さないとカードが終わらず、デザートの帯が出ない（テストで確認）
- 選択肢：ア) 厨房が作る → 今のまま／イ) ホールが作る → ドリンクを「全部できた」の条件から外し、ホールの画面に出す／ウ) ドリンクは KDS に出さない
- 推し：答えに合わせる（ホールならイ）

#### Q4. 経過時間で色を変えるのは何分？ 赤い帯は点滅させる？（#295、要件 Q-02）

- 背景：今は **5分で琥珀、10分で赤**。土鍋は提供まで25〜30分かかるので、ほぼ全部のカードが途中で赤くなり、本当に遅れている卓が分からない（テストで観察）。この値は5月から「オーナー確認中」のまま（`docs/要件定義書.md` Q-02）
- **推し：琥珀20分・赤30分**（土鍋の目安と「来店から30分以内」の目標に合わせる）。値を変えるだけなので、その場で決まればすぐ直せる
- 点滅：7/16 に「赤チカを削除」と決めた。速い点滅は消したが、10分を超えた帯は今も**2秒周期でゆっくり明るさが変わる**（8/23 から。`kds-a-grid.html` の `alertBannerBlink`）。「ゆっくりならよいか、完全に止めるか」を聞く。推し：決定どおり止める

#### Q5. アレルギーはどう目立たせる？ 紙には必ず刷る？（#294）

- 背景：今は品目のアレルギーが、ふつうの備考（「ご飯少なめ」など）と**同じ灰色の小さい字**で出る。チビ伝は「備考を刷らない」設定にするとアレルギーも刷られない。数量2以上のとき、どの膳のアレルギーか分からない
- 聞くこと：(1) 厨房でどう目立たせたいか（色・印）、(2) 備考を刷らない設定でもアレルギーは刷るか、(3) 2膳以上のとき、どの膳かをどう伝えたいか（注文を分けてもらう運用か、注文端末チームとの調整が要る）
- **推し**：画面は予約のアレルギーと同じ赤の強調にする。紙は設定に関係なく、品名と同じ大きさで必ず刷る。**下書きを作ってある**（ブランチ `feat/kds-allergy-emphasis`。紙は「【アレルギー】えび」を独立した太字の行にする）

#### Q6. 大量注文で土鍋をコンロから降ろして蒸らすとき（#161・7/16 の未決）

## 第2部 TableCheck の予約をどう取り込むか（本命：CSV）

> **打合せの後の決定（2026-10-21）**：予約は CSV で取り込み、変更があったときは CSV を再度取り込む → [決定の記録](2026-10-21_決定_予約のCSV取込と変更の反映.md)

### 2-1 経緯と、最初に確かめること

- 6/4：予約は「管理画面を見て手で転記」と決めた → 6/18〜7/16：TableCheck API で取り込む方向へ進んだ（事前メニュー・人数区分・状態が取れることは確認済み）→ 料金・API 申請・アレルギーの欄が未決のまま → **10/11 に API 連携をやめた**
- **やめた理由はどこにも書かれていない**（コミット・PR #274・README・Issue）。料金や申請の手間が理由だと推測しているが、**最初に確かめる**。理由が料金なら、CSV（管理画面の機能）が代わりの道として筋が通る
- 7/16 の Q1〜Q9（契約・申請・料金など）は記録が無い（議事録に「持ち越し」）。API をやめたので多くは不要になったが、Q4「予約フォームのアレルギーの設問・メニュー明細の実物」は CSV でも必要

### 2-2 取り込み方の比べ

試作は予約入力画面 `/reservations` に4つの入口を並べてある（`relay-server/README.md`「予約の入口(試作・4方式)」）。どれも実物の TableCheck のデータでは試していない。

| | A 手入力 | **B CSV** | C 貼り付け | D メール |
| :--- | :--- | :--- | :--- | :--- |
| 店の手間 | 予約1件ごと（新規・変更・取消のたび） | 1日1〜数回。TableCheck で出力 → ダウンロード → `/reservations` に上げる → 確認画面 → 取り込む | 1件ごと。予約詳細の文面を貼る | 1件ごと。通知メールを取込フォルダへ保存 |
| 遅れ | 入れたらすぐ（5秒ほどで KDS へ） | **出力した時点のまま**。次に出すまで変更・取消は届かない | すぐ | 保存して人が確かめたとき |
| 取れる項目 | 全部（日時・大人/子供・名前・メニュー・アレルギー・要望・メモ・卓番） | **列は不明**（下の 2-3） | 「項目名: 値」の行で読めたものだけ | 通知メールの本文次第（実物を見ていない） |
| 主な誤り | 写し間違い・入れ忘れ | 列の取り違え・取消の出方（下の 2-6） | ラベルが合わず読めない | 件名でしか取消を判定しない |
| 試作 | 動く | 動く。UTF-8 と Shift_JIS を自動判定、取り込む前に確認画面 | 動く | 動く |

**推し**：前日までの予約は **B（CSV）**、当日の電話予約は **A（手入力）** の併用（2-4）。

### 2-3 CSV で行くなら：その場で確かめること（管理画面を開いてもらう）

公開情報で分かっていること：TableCheck の公式ヘルプに、予約一覧（All Reservations）を Excel/CSV で出す手順がある。**1回に出せるのは最大2か月分**、**ダウンロードできるのは Shop Manager / Franchise Manager の権限の人だけ**（[TableCheck ヘルプ](https://support-restaurants.tablecheck.com/hc/en-us/articles/900002275703-Generating-All-Reservations-Report)）。日本語の画面では「予約検索・出力」から CSV を出す手順を書いた他社の資料がある（65日ずつ。[RESZAIKO の移行手順](https://reszaiko.zendesk.com/hc/ja/articles/45465472110099)）。**列の一覧と文字コードは公開されていない**ので、店の画面で見せてもらう。

1. **出せるか・誰が出すか**：この契約で予約の CSV 出力が使えるか。Shop Manager 以上のログインを持つのは誰か（オーナーだけか、ホールにも渡すか）
2. **受け取り方**：その場でダウンロードか、メールで届くか。何分かかるか
3. **列の一覧（見出し行）**。特に見る所
   - 予約番号の列があるか（無いと取り直しで二重になる）
   - 来店日・時刻の列名。「作成日時」「更新日時」の列もあるか（試作が来店日時と取り違えるおそれ。2-6）
   - 名前は1列か、姓・名に分かれるか
   - 人数の区分（大人・シニア・子供・幼児）
   - **コース名と数量**。1予約に複数のコースがあるとき、1つのセルにどう並ぶか
   - **アレルギーが独立した列か**、予約メモに混ざるか
   - ステータスの値の種類（確定・キャンセル・来店など）
   - 卓番の列
   - 電話・メールの列。**出力から外せるか**
4. **形式と文字コード**：CSV か Excel か、Shift_JIS か UTF-8 か（試作はどちらも読める）
5. **範囲**：当日分・翌日分だけを出せるか。ステータスで絞れるか
6. **取消・変更の出方**：取り消した予約は「キャンセル」の行で出るか、出力から消えるか。時刻を変えても予約番号は同じか
7. **運用**：誰が何時に1日何回出すか（例：開店前に1回、夜の営業の前に1回）。どの端末で取り込むか（店内 LAN の端末である必要がある）
8. **子どもの区分**：TableCheck の「子供」「幼児」の年齢の決め方。こちらの「子ども」は0〜2歳の1区分（`docs/db-design.md`）。TableCheck の「子供」を大人と子ども、どちらに数えるか
9. **コース名**：TableCheck のコース名が KDS の品名（「〜御膳」など）と同じか。炊飯準備の合図は品名で判定しているので、名前が違うと合図が出ない
10. **サンプルを1つもらう**：1日分の見出し行と2〜3行。名前・電話・メールはダミーに置き換えてもらう（2-5）

### 2-4 CSV では間に合わない予約（当日の電話予約・来店後の予約）

- 6/3：当日予約が多く、メニュー付きが多い。受けるのはホール／中間スタッフ（[運用確認](2026-06-03_運用確認_電源充電・KDS台数.md) C）
- 今の穴：KDS の「＋」で入れた予約は、その端末にしか残らない。厨房に炊飯準備の合図が出ない。日付も入れられない（#292）
- 決めること
  1. **当日予約の入口**：ア) 予約入力画面 `/reservations` だけにする／イ) KDS の「＋」からも中継サーバーへ登録する。**推し：イ**（6/3 に店は「ホールのモニターから入れたい」と言っている）
  2. **電話予約を TableCheck にも入れるか**：入れると、次の CSV に同じ予約が載って二重になる。対策の候補は、手入力に TableCheck の予約番号を書ける欄を付けるか、「当日分は CSV で取り込まない」と線を引くか
  3. CSV を出した後の変更・取消：手入力で直すか、CSV を出し直すか（出し直すと、手で直した卓番・取消が上書きされる。2-6）

### 2-5 個人情報の扱いで決めること

- 試作は電話・メールを取り込まない（厨房で使わないため）。CSV ファイルそのものはサーバーに保存しない。過ぎた日の予約は消える
- 決めること
  1. TableCheck から落とした CSV（電話・メール入りの可能性が高い）を**どの端末のどこに置き、取り込んだ後に誰がいつ消すか**
  2. 電話・メールを出力から外せるか
  3. 名前をどこまで出すか（フルネーム・姓だけ・かな）。KDS と予約ストックに表示される
  4. 開発用のサンプルの受け渡し方（ダミーに置き換え、メールに直接添付しない、使い終わったら消す。リポジトリには実データを載せない）
  5. 店内 Wi-Fi を客と共用するなら、中継サーバーのトークン（`auth.token`）を必ず設定する（設定しないと予約の名前・アレルギーが LAN 上で見える）

### 2-6 こちらの宿題（店には聞かない。CSV の実物が来たら直す）

仮の列名で試作の CSV 取込を動かして分かった穴（2026-10-21、コードで確認）。

- 「来店日」「時刻」が別の列で、ほかに「作成日時」の列があると、**作成日時を来店日時と取り違える**（列名の部分一致で「日時」に当たる）
- 取り直しは予約番号での上書きなので、**手で取り消した予約が、CSV がまだ「確定」なら生き返る**。手で入れた卓番も消える
- CSV から消えた予約は消えない（差分で消す処理が無い）
- 予約番号の列が無いと、日時と名前で予約を見分ける。時刻や名前が変わると二重になる
- 手入力した予約を後から CSV でも取り込むと二重になる（炊飯準備の合図も2つ出る）
- コース名にカンマや読点があると、品目が割れる
- アレルギーが予約メモに混ざっていると、アレルギーとして目立たない
- 「シニア」「幼児」の列を読む修正（10/13）は、まだ commit されていない（`pokapoka-worktrees/feature-reservation-intake` に残っている）
- 文書が古い：`README.md`・`relay-server/README.md` の冒頭が「入口は未設計」のまま。試し方の `git switch feature/reservation-intake` はもう要らない
