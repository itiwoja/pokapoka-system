# 提供ルール：大人1名1膳（お願いベースで確定）と提供順（前菜 → 膳 → デザート）

> 出典：オーナー／店舗からの運用ルール共有（2026-09-03）。
> 関連：[2026-06-04 議事録 §5](2026-06-04_議事録.md)（「大人1名1膳必須」の確定） / [2026-07-16 議事録 §2](2026-07-16_議事録_使用感デモ・UI方針.md)（食後デザートのホール側表示） / [要件定義（仮） 注意事項](../要件定義（仮）.md)

**一言サマリ**：注文ルールは **大人1名1膳を「確定でお願いします」とお客様に依頼**する運用。提供は必ず **前菜 → 注文された膳 → デザート** の順で流れる。**前菜とデザートは「注文」ではなく提供フローの一部**であり、注文データにも KDS のレーン分類にも存在しないのが現状。

---

## 1. 注文ルール：大人1名1膳（確定）

- **大人の方は 1 人 1 膳のご注文をお願いしている**（お客様への依頼としてお伝えし、確定扱い）。
- 子供とのシェアは可（[要件定義（仮）](../要件定義（仮）.md) の予約フォーム注意事項）。
- システム側の扱いは既定：**注文時に人数分のメニューが揃うまで確定不可**のバリデーション（[2026-06-04 議事録 §5](2026-06-04_議事録.md)）。人数の大人/子供内訳（`reservations.adults` / `kids`）と連動する（[db-design](../docs/db-design.md)）。

## 2. 提供順（確定）

```
前菜  →  注文された膳  →  デザート
```

- **前菜**：膳の前に必ず提供する。お客様の個別注文ではなく、**来店したら出るもの**。
- **膳**：お客様がタブレットで注文した品。大人1名につき1膳。
- **デザート**：膳をすべて出し終えた後に提供する（＝食後）。

## 4. 確認結果と実装方針（2026-09-03 決定）

§3 の論点は以下のとおり決着し、KDS に実装した。

| 論点 | 決定 |
| :--- | :--- |
| 前菜は誰に出すか | **子供にも出す。全員分**（大人＋子供の合計人数）。KDS では `order.people` がこの合計値にあたる |
| 粒度 | **「出した / 出してない」の2値**。個数管理はしない。6名卓で前菜を何個出したかを厨房が数える必要は実運用上ないため |
| KDS 上で可視化するか | **する**（出し忘れ防止） |
| デザート案内の表示先 | **KDS のホール画面**。客側タブレットは別チーム管轄のため本リポジトリのスコープ外（§3 の資料割れは「ホール側」で確定） |

### 実装方式：cue 方式

**前菜・デザートは注文品目として持たない。** 注文データを汚さず、`itemCategory()` のレーン分類にも触らずに済むため、既存の
炊飯cue（#159）・全品完了ホールcue（#152）と同じ「カードに貼る帯」として表現する。

- **前菜cue**：進行中カードの**品目リストの上**に `前菜 ×N名` を出す（膳より先に出すことを配置で示す）。キッチン画面とホールの進行中カードの両方に出る
- **デザートcue**：ホール画面の「提供準備完了」カードに `デザート ×N名` を出す。膳を出し終えた直後＝デザートのタイミングであり、§3 の「最後の1ステップ」にあたる
- 状態は `kds_serve_cue_v1`（当日分のみ）に保持し、BroadcastChannel で端末間同期する
- **提供はホールの動作**のため、炊飯cue（キッチン専用）と違い権限モードで弾かない

### 残っている論点

- 前菜・デザートの**メニュー内容そのもの**（何を出すか）はシステム管理外。現状どおり店舗運用で決める
- 客側タブレットへのデザート案内は別チーム側の実装。連携が必要になった場合は改めて設計する
