# pokapoka-system

沖縄みらいAI＆IT専門学校が土鍋飯ぽかぽか様のオーダーシステムを制作するためのリポジトリ。

> **本リポジトリのスコープは「厨房端末（KDS）画面」「店内中継サーバー」「注文端末からの通信モジュール」「予約の入力・管理用画面」**です。別チームの注文端末・注文サーバーは `order-terminal/` サブモジュールで参照します。
> 現況・最新決定・未決事項は [現在地](knowledge/現状.md) を参照してください。2026-10-21 に決まった Linux サーバー運用・Next.js 移行は、導入手順や移行範囲・時期の確認待ちであり、以下は現行の Node.js / HTML 実装の説明です。

## 構成

注文端末→既存の注文サーバー（3001番）の送信仕様は、商品ID・選択肢ID・個数・人数・卓番・再送IDで確定しています（[接続先と仕様の案内](docs/注文端末_注文サーバー接続.md)）。商品名・価格は注文サーバーの商品マスターで解決します。注文サーバーは保存成功後に中継サーバー（8000番）へ転送します（`RELAY_ORDERS_URL` の設定が必要）。[独立したモックDB](docs/order-database.md)はこの経路に接続していません。

## KDS（厨房オーダー表示システム）

**`kds-a-grid.html`** が本線の KDS 画面です。HTML / CSS / JavaScript のみ（フレームワーク・外部CDN不使用）で、伝票描画の `slip-renderer.js`、人数計算の `relay-server/party-size.js`、通知音の同梱ファイルを参照します。HTML 1ファイルだけで全機能は完結しません。中継サーバーから配信して使用し、通信断時は取得済みの表示・手元の操作状態を保持しますが、新着注文・別端末同期・サーバー経由の印刷には接続が必要です。店舗実機での合否は [実機検証チェックシート](docs/実機検証チェックシート_受け入れ試験.md) で別途確認します。

**産業用計器 UI**（商用デシャップ Okage DDS を参考にした、明るい盤面・色は「意味」にのみ使う設計）の部品構成に、**Java Swing（Metal / Ocean テーマ）風の見た目**を重ねています（青グラデーションのボタン、内部フレーム風のカード見出しとバンプ、Flush3D 枠の入力欄など。`<style>` 末尾の上書き層）。カードグリッド＋予約ストックの2ペイン構成。緊急度＝カード上帯（緑→琥珀→赤）、種別＝**カード背景のトーン差（新規=淡青／予約=淡金）**＋アンダーライン/チップ、赤は「10分超の経過警告」専用。

主な機能:

- 複数個品目は品目タップで `0/3→1/3→2/3→完了` と数え上げ（長押しで誤タップを1個戻す）。全完了カードは厨房では非表示、ホールではデザート提供まで保持
- コンロ番号（1〜10）の割当とタイマー管理。タップで `未使用 → コンロ使用中(黒) → タイマー管理中(赤) → 未使用` と循環します。**コンロ枠とタイマー枠は同じ番号でも別資源**として独立にロックします（#145）。卓Aがコンロ1番を使っていても卓Bはタイマー1番を使えます。埋まっている種別はタップ時に自動で読み飛ばし、**両方が他卓で埋まっている番号だけ**が押下不可になります。HUD はコンロ列とタイマー列を並べ、稼働中の番号だけを卓番付きで表示します（無いときは「なし」）。カード側の割当は、サブ行の「コンロ割当」で1〜10を展開して行います
- 予約ストック→進行中への配膳移動（卓番は誤入力防止の**ダイヤルUI**で選択）
- キッチン/ホール権限モード、ホールでの前菜・デザート提供確認とチビ伝の印刷（プレビュー＋実機印刷、未設定・失敗時は `window.print()`）
- 経過時間による色アラート、**10分超は上段バナーの静的な赤塗り**
- **グリッド/レーン表示切替（カテゴリ別）**
- LocalStorage + BroadcastChannel による同一originの2タブ同期。別端末の厨房状態は中継サーバー経由で同期（前菜・デザート提供確認等は対象外）

デモ／メニューデータは実メニュー（山城牛の土鍋御膳／単品／ドリンク）を使用しています。

### 動作確認

```sh
# 初回のみ依存関係を導入する
npm --prefix relay-server ci
# 注文APIとKDSを同じサーバーで起動する
npm start
# 起動ログに表示されたURLを開く（既定値は http://127.0.0.1:8000）
# /          … KDS（デシャップ）
# /api/health … 中継サーバーの稼働確認
```

`order-client.js` を使う検証端末は同じ接続先の `/api/orders` に送信します。実注文端末は3001番の注文サーバーへ送り、そこから8000番へ転送します。`config/config.json` の
`server.host` が `auto` の場合は、起動ログに表示されたLAN IPを両端末で使用してください。
`python -m http.server` は静的ファイル専用で、注文APIは動作しません。
8000番を別サーバーが使用している場合は、そのサーバーを停止してから `npm start` を実行してください。

### 自動テスト

GitHub Actions は Pull Request と `main` への push で Node.js 22 を使用し、
中継サーバーとルートの KDS 関連テストを実行します。店舗の設定ファイル、認証情報、
外部 API は不要です。ローカルでもリポジトリ直下から同じテストを再現できます。

```sh
npm --prefix relay-server ci
npm test
```

`npm run test:kds` / `npm run test:relay` で個別にも実行できます。

`npm ci` は `relay-server/package-lock.json` に固定された依存関係をクリーンに導入します。
いずれかのテストが失敗するとコマンドと GitHub Actions は非ゼロ終了します。

`window.KDS_ORDERS` に注文データ（`{id, table, type, start, people, items:[{name, qty, options, allergies, done}]}`）を投入すると表示されます。アレルギー情報は `allergies`（`allergy` / `allergyInfo`・配列も可）で受け取り、品目直下に「アレルギー: …」として常時表示します。空の場合は「デモデータを投入」ボタンでサンプルを表示できます（中継サーバー配信時は自動デモを抑止）。

## 予約ストック（TableCheck APIは中止・ファイル取込を利用）

> **2026-10-11: TableCheck API連携は中止。2026-10-21: 予約は主にCSVで取り込み、変更時は取り込み直す方針に決定。** 朝に1回当日分を確認・取り込みます。手入力も併用しますが、当日の電話予約の扱い等は確認中です（[決定記録](knowledge/2026-10-21_決定_予約のCSV取込と変更の反映.md)）。
> TableCheck の実API取得処理・疎通確認・暫定契約の文書は [`archive/tablecheck/`](archive/tablecheck/README.md) へ退避した。

`relay-server/` は予約を SQLite（`data/reservations.sqlite`）に保存し、当日の `booked` かつメニューありの予約を KDS の予約ストックへ流し込みます。`/reservations` に手入力・CSV／Excel（.xlsx）取込・貼り付け・メールの入口と予約一覧・変更・取消を試作済みです。再取込で消えた予約の扱いや、手修正した卓番・メモの保護等は未対応です。旧API取得・モック・`/demo` は [`archive/tablecheck/`](archive/tablecheck/README.md) に退避しましたが、TableCheck の書き出しファイル取込は現行機能です。**Node 22.13+** が必要です。

```
【予約の入力】             【店内ミニPC = 中継サーバー】          【KDS端末】
CSV／Excel・手入力等 ──▶ /reservations ──▶ data/reservations.sqlite
                         server.js ── /api/stock(当日分) ──▶ kds-bridge.js → 予約ストックへ
```

- 予約は**朝に1回**取り込む
- 手入力も試作済み。必要な入力項目は時間・人数・名前・メニュー（あれば）・メモ
- `/reservations` には一覧・変更・取消の試作がある。正式な管理用画面の内容と運用は未設計
- 予約のアレルギー（`allergies`）と要望（`request`）は、予約ストック・厨房カードへ常時表示する
- **relayの待受先（host/port）は `config/config.json` に集約**（雛形: `config/config.example.json`。優先順位は 既定値 < config.json < 環境変数）。実注文端末の送信先と、注文サーバーの `RELAY_ORDERS_URL` は [別チーム側で設定](docs/注文端末_注文サーバー接続.md)する
- 起動方法・エンドポイント・LAN 配信時の注意（固定IP・ファイアウォール）は [relay-server/README.md](relay-server/README.md) を参照

### データ保存方針: 中継サーバーと注文サーバーを区別する

2026-06-18 の非保存方針から変更し、現在は**予約を中継サーバーの SQLite に保存**して再起動後も保持します。TableCheck が元の予約を管理し、このSQLiteは店内へ取り込んだ予約・手入力予約の保存先です。`/api/stock` 取得時に過去日の予約を削除します。故障に備え、停止中のコピーか SQLite のバックアップ機能で別媒体へ退避してください（[手順](relay-server/README.md#予約の保存reservation-storejs)）。中継サーバーは注文を履歴としては保存しませんが、営業中に再起動しても KDS から当日の注文が消えないよう、**当日分の控えを SQLite（`data/orders.sqlite`）に残し**、保持時間（既定720分）を過ぎた分は自動で削除します（2026-10-17）。厨房状態はメモリのみです。別チームの注文サーバーは注文を PostgreSQL に保存します。監査ログ・印刷設定も別途ファイル保存します（[データ配置](docs/db-design.md#13-データ配置)）。

## 提供時間の自動計測（Issue #29）

注文受付（`start`）から**全品目完了までの提供時間を自動記録**し、LocalStorage（キー `kds_serve_log_v1`）へ追記保存します。PRD の KPI「平均提供時間 MVP前比20%減」の**導入前ベースラインデータ**として用います。

- 全品目をタップ完了した瞬間に、完了時刻・提供時間（`serveMs`）・営業日（`day`）を記録
- `orderId` で重複ガード（2タブ同期・再完了での二重計上を防止）。判定は**当日分のみ**を見る（POS の注文 ID が日次リセットの連番でも記録を取りこぼさないため #179）
- ヘッダーの表示ボタンは削除済み（#112）。参照・エクスポートは下記のコンソールアクセサから行う

### 保持期間（#179）

ログは**直近14日ぶん（暦日）・最大3000件**に自動でローテーションします（`SERVE_KEEP_DAYS` / `SERVE_MAX_RECORDS`）。営業日だけを数える仕組みではありません。切り詰めは起動時と日付が変わったときに走ります。

無期限に貯めると localStorage の 5MB 上限に達し、その時点で**完了状態・コンロ・並び順・予約ストックの保存が全機能まとめて止まります**（画面はメモリ上の状態を描き続けるので、リロードするまで気付けない）。**それより長期の KPI データが要る場合は、CSV に書き出して localStorage の外へ退避してください。**

保存に失敗した場合は握り潰さず、`console.error` を出したうえでヘッダーに赤い警告バナーを表示します。容量不足のときは提供時間ログを当日分まで削って 1 度だけ再試行します。

計測ロジックは `kds-a-grid.html` にインライン実装（単一HTML要件のため）していますが、同一ロジックを `serve-log.js` に切り出して Node テストで検証しています。

```sh
node --test tests/serve-log.test.js
```

コンソールからの参照用アクセサ:

```js
window.KDS_getServeLog()    // 記録レコード配列
window.KDS_getServeStats()  // 件数・平均・最大・最小・10分超件数
window.KDS_exportServeCSV() // CSV ダウンロード
window.KDS_clearServeLog()  // ログ全消去
```

> **注**: `serve-log.js` は Node テスト用の参照実装です。`kds-a-grid.html` 内のインライン版とロジックは同一なので、片方を変更したら両方（と `tests/serve-log.test.js`）を同期してください。

## 遅延アラート：10分超の静的な赤表示（Issue #12・#158）

厨房が「見ていない瞬間」の提供遅延に気付けるよう、経過10分超のカードを強調します。

- **静的な赤**: 10分超カードの上段バナーを赤塗りに（明滅は 2026-07-16 打合せの決定により、外枠アウトラインはオーナー指示により Issue #158 で廃止）
- タイマーロック中のカードは経過時間を更新しない（＝確認済み扱い）

> 10分超の遅延ビープはありません。**新着注文の通知音は実装済み**で、「通知音ON」を押すと同梱のししおどし音を使います。初回スナップショット・同一ID再送・変化のないポーリングでは鳴らしません。

## レーン表示：カテゴリ別分割（Issue #13）

ヘッダーの **「グリッド／レーン」** 切替で、注文カードのグリッドとは別に、**未完了品目をカテゴリ別3レーンに横断表示**できます。コンロ側・中間スタッフ側での作業分担が目的です。

- 3レーン: **🍚 ご飯類**（土鍋御膳・ご飯もの）／**🍢 サイド**（単品）／**🥤 ドリンク**
- 各レーンに未完了品目を **[卓番] 品名 ×残数（＋オプション）** で並べ、経過時間レベルで左枠を色分け
- 品目タップで1個ずつカウントダウン（`doneMap` を共有）→ 残数0でレーンから消える。グリッドと状態・2タブ同期は共通
- 表示モードは LocalStorage に永続

> relayの注文フィードにカテゴリは無いため、KDS 内の分類関数（`itemCategory`）で自動判定します（実メニュー基準・未知はサイドへ）。メニューが増えたら分類キーワードの追記を検討してください。POS連携は行いません。

注文は `/ws/orders` で即時配信し、切断中はHTTP取得で補完します。導入時は `relay-server` で `npm ci` を実行してください（[詳細](relay-server/README.md#注文のwebsocket配信)）。
